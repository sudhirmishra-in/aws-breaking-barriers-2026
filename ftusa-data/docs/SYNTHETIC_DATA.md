# Synthetic raw data generator

Run from ftusa-data using Python 3.12+ and the project's installed dependencies:

```bash
python -m ftusa_data.synthetic --raw synthetic/raw --standards-from raw --out synthetic/out --seed 42
python -m c3.load --tables synthetic/out/tables --dry-run --dump synthetic/load_dryrun
python -m pytest tests/test_synthetic.py -q
```

Both target directories must be new. Existing real raw/out directories are never overwritten. Choose a new directory for subsequent generations. No AWS or model calls occur during generation. The generator reads only the actual APS/FPS reference workbooks; no customer CSV rows are copied. Its seven CSV schemas match the fields consumed by the existing pipeline (not every unused column of the original exports). Synthetic and customer exports converge at the same processed-table and C3 item contracts.

## Data and validation

12 fictional accounts (six profiles and six peers); 12 matching projects in each source export; all five priority countries and three priority crops; smallholder, cooperative, estate and processor profiles. 88 valid responses plus 15 deliberately invalid responses; five account-year summaries, including one below the 10-response threshold; seven accounts without surveys. Expected harvest-decrease percentages are 60, 30, 20, suppressed, and 40. Fixed seed, fixed dates, independent SYN IDs, deterministic CSV contents. Real standard workbooks are copied byte-for-byte and checksummed; clauses are never fabricated.

`--out` invokes the actual existing pipeline, corrects its hard-coded FTUSA source labels to synthetic in CSV and existing Parquet outputs, adds data_origin, validates known percentages, exclusions, suppression and C3 item schemas. Use this combined command for synthetic builds: directly invoking ftusa_data.run would retain its original FTUSA source labels. The data dictionary is generated by the original pipeline and does not document the additional data_origin column; this document defines it as the dataset provenance enum value synthetic.

synthetic_manifest.json records input hashes and provenance. expected.json contains independent arithmetic expectations. scenarios.json supplies three full-exchange role-play scripts (one Spanish), plus decline, fictional email PII, private-scope and out-of-scope cases. synthetic_validation.json records executed checks and explicitly unverified areas. Generated organization labels and project text visibly indicate fictional/synthetic data. Current C3 item shaping does not propagate data_origin; preserve the manifest with the deployment and use a separate synthetic store/index to avoid mixing origins.

## Requirement mapping and integration responsibilities

Vision: three role-play scenarios, Spanish, same-challenge/different-profile comparison, corrected playback, per-claim citations and standard references, consent, PII flag without redaction, pending human review, feedback, exactly one write-back with source='agent conversation'. The generator supplies inputs and assertion specifications; actual conversations and write-back records must be generated by the running agent. Scripts are not evidence that these end-to-end requirements passed.

Technical: Python 3.12+, no direct third-party model API, synthetic producer data and supplied real reference standards. Existing ETL outputs feed the existing loader and data tools. No regional measurements are fabricated: public regional evidence and standards retrieval must be integrated by their respective components. Regional centroids remain the pipeline's approximate manual coordinates.

The challenge-tag vocabulary remains the existing 11-tag contract. Scenario labels are draft expectations, not a human-labeled benchmark; the required >=80% conversation-tag agreement remains unverified and requires a human-reviewed evaluation set. Three scripts are not sufficient to measure all 11 tags reliably. No AWS deployment, CDK stack, AgentCore runtime, external evidence, consent implementation or write-back implementation is supplied by this generator.

Existing compatibility issues discovered: surveys.build raises on questions whose ranking is empty across all accounts (e.g. all answers Other); normal generated questions therefore include a valid ranked choice. Crop Diversification tagging remains pending FTUSA confirmation. Original standards-parser warnings are retained in report.json. Entity-to-standard mapping reuses the existing project's interpretation of FPS as Factory Production Standard; resolve differing terminology in the Vision document with FTUSA.

FTUSA replacement: generate the synthetic dataset into its own directory, then later run ftusa_data.run on the approved FTUSA export directory and select that output directory in c3.load. Do not concatenate the datasets or reuse a shared mutable AWS target without reviewing the loader's stale-record sweep. Team agreement on the schema and cloud acceptance testing are still required.
